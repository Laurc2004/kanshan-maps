# 一图看山产品决策与 Agent 优化方案

日期：2026-09-13
状态：方案评审稿
目标：围绕知乎黑客松，收缩产品范围，提升生成稳定性、个性化价值和助手改图成功率。

## 1. 结论先行

产品不再突出“智能编排”作为用户功能入口，保留两条核心能力：

1. 观点对照：帮助用户看清一个知乎问题中的共识、分歧、前提和证据。
2. 学习路线：结合用户目标和知乎资料，告诉用户下一步学什么、为什么学、如何验证学会。

Harness 保留为底层执行架构，但不要求每次生成完全相同的图形结构。要求是：输入和引用可追溯、输出内容有证据、布局稳定、结果可编辑。

产品主叙事建议从“通用知识图生成器”改为：

> 把知乎里收藏过、关注过、却没有真正消化的知识，变成看得懂的观点和走得下去的学习路线。

观点对照是辨识度最高的能力；“收藏夹到可执行学习路线”是最值得拿奖的知乎生态亮点。

## 2. 产品范围取舍

### 保留

- 观点对照图
- 学习路线图
- 知乎回答、关注答主、收藏夹等生态数据的个性化入口
- 可点击原文引用
- 可编辑画布
- 看山助手的安全改图能力
- 生成过程的阶段反馈

### 收缩

- 不再把智能编排作为用户可选择的独立模式
- 不再承诺任意问题都能生成任意图类型
- 不强制固定节点数、固定分组数或固定模板
- 不为了填满画布而生成低信息量节点

### 暂缓

- 多 Agent 辩论
- 复杂兴趣人格画像
- 多人协作
- 大量图类型
- 自动推断“用户已经掌握了什么”

## 3. 两条专用 Harness

### 3.1 观点对照

目标不是把回答摘要成卡片，而是回答：

- 大家真正同意什么？
- 分歧在哪里？
- 分歧来自价值判断、事实证据，还是适用条件不同？
- 哪些观点有明确原文依据？

生成策略：

- 先对来源去重、过滤无判断内容和低相关内容。
- 根据素材决定结构：真正对立时使用左右阵营；条件不同导致结论不同，则使用前提对照；观点高度一致时展示共同结论和少数异议。
- 每个关键节点至少绑定一个真实引用。
- 节点数量由信息密度决定，宁少勿凑。
- 边只表达必要关系，避免蜘蛛网。

### 3.2 学习路线

目标不是固定输出“入门—进阶—精通”，而是围绕用户目标给出行动顺序。

可根据用户状态选择结构：

- 小白：先修知识、最小实践、反馈检查。
- 有基础：跳过已掌握内容，补短板。
- 有明确目标：从交付成果倒推知识和任务。
- 资料很多：去重、排序、标记必读与选读。

每个阶段应包含：

- 学什么
- 为什么现在学
- 推荐的知乎原文
- 一个可验证的小任务
- 何时可以进入下一阶段

“收藏过”不能等同于“读过”，也不能等同于“掌握”。用户应能手动标记已掌握、跳过和想深入。

### 3.3 Harness 原则

- 内容结构自适应，数据契约稳定。
- 模型输出内容和关系，程序负责 ID、引用、布局、长度、碰撞和安全校验。
- 默认一次生成可用结果；只有失败或用户主动深入时才追加模型调用。
- 流式体验优先展示“首个可用结果”，不是展示未完成的半个 JSON。
- 生成失败时保留来源和明确错误，不生成看似完整的幻觉图。

## 4. 模型与速度策略

当前 DeepSeek V4 Flash 适合作为默认模型，暂不建议仅凭模型名称直接切换。应先优化调用方式，再以真实样例做对照测试。

### 当前主要瓶颈

- 输入素材过长会增加首字延迟和结构错误。
- 骨架与详情两阶段串行调用虽然能较早显示卡片，但完整结果仍需等待第二次调用。
- 当前 OpenAI 兼容调用使用 `stream: false`，SSE 主要是阶段通知，并非模型内容真正流式返回。
- 通用 Harness 让模型承担了过多规划和结构选择工作。

### 推荐方案

1. 预处理素材
   - 去重。
   - 删除只有态度、没有论据的重复文本。
   - 为模型提供必要段落，而不是整篇回答。
   - 默认只使用高相关来源，其他来源按需补充。

2. 默认一次生成短结果
   - 首次生成同时包含标题、分组、短描述和引用。
   - 只在校验失败、引用不足或用户点击“深入分析”时追加调用。

3. 真流式按完整单元提交
   - 模型产出一张完整卡片后才展示。
   - 不把未完成 JSON 直接注入画布。
   - 如果底层接口无法稳定输出结构化流，则保留阶段 SSE，但明确展示“正在形成观点”，不伪装成已完成内容。

4. 困难任务升级模型
   - Flash 负责默认生成。
   - 观点高度混杂、结构校验失败或用户请求深入论证时，才使用更强模型或知乎直答深度模型。
   - 升级模型必须有触发原因和预算上限。

### 评估指标

不要只看 JSON 是否合法。至少记录：

- 首个可用节点出现时间
- 完整结果时间
- 引用覆盖率
- 引用是否支持对应描述
- 重复节点比例
- 用户是否需要再次修改
- 生成失败率

## 5. 知乎生态个性化

### 5.1 第一优先：收藏夹到学习路线

用户选择一个知乎收藏夹，补充一个目标，例如“我想做出一个能用的 Agent”，系统输出：

- 收藏内容对应的学习阶段
- 重复资料和可跳过内容
- 当前目标缺失的知识
- 下一步可执行任务
- 每一步返回知乎原文

对于没有收藏夹或授权数据不足的用户，保留问题搜索作为冷启动路径，不让产品失去可用性。

### 5.2 第二优先：关注答主观点对照

在观点图中提供“全部观点”和“我关注的答主”切换：

- 高亮本次素材中的关注答主。
- 显示关注答主与其他来源是否存在不同前提或反例。
- 没找到关注答主时，只说“本次素材中未发现”，不推断其没有观点。
- 不把未关注自动标为反方。

### 5.3 第三优先：我的学习地图

记录用户明确做过的行为：

- 学习目标
- 已掌握节点
- 想深入的分歧
- 保存的原文
- 已完成的小任务

先做显式标记，不急于做复杂自动画像。个人数据默认私密，分享时单独选择是否带出。

## 6. 看山助手现状诊断

当前助手问题位于四个层面。

### 6.1 意图层

当前请求直接把完整 graph、最近对话和操作规则交给模型，让模型直接猜操作。没有先区分：

- 内容修改
- 结构修改
- 视觉修改
- 解释问题
- 信息不足需要追问

因此“把第一个立场标为重点”“删掉最弱的立场”“为什么会有这个分歧”容易被映射成相近但错误的操作。

### 6.2 协议层

当前 legacy viewpoint 使用 index，新 KnowledgeGraph 使用 nodeId。两套 prompt、parser 和 apply 逻辑并存，同一类自然语言在不同图类型上的行为可能不一致。

`update_node` 使用 `Partial<KnowledgeNode>`，权限过宽，模型可能在用户只要求精简时同时修改标题、正文、分组和引用。

### 6.3 执行层

`applyKnowledgeGraphOps` 当前允许操作逐条部分成功。多步结构修改中间失败时，前面的修改仍会提交，可能得到半完成图。

`reset` 混在模型操作协议中，语义是恢复本条消息前的图，但用户可能把它理解为撤销上一步或恢复初始图。

### 6.4 画布层

内容更新后通常重新走渲染和布局：

- 用户手动移动过节点，改一个标题可能导致全图位置变化。
- `relayout` 与普通内容修改没有清晰边界。
- 画布上看到的变化可能不符合助手回复中的描述。
- 快速连续请求存在旧响应覆盖新状态的风险。

## 7. Agent 2.0 方案

看山助手应定位为“带变更预览和安全提交的知识图编辑器”，而不是万能聊天机器人。

### 7.1 新流程

```text
用户请求
  -> 意图识别
  -> 结构化任务
  -> 读取图摘要和节点目录
  -> 生成候选变更
  -> 确定性校验与风险分级
  -> 低风险直接应用 / 高风险预览确认
  -> 局部重渲染
  -> 返回解释和变更记录
```

### 7.2 响应类型

建议从“永远输出 ops”改成四种结果：

- `apply`：可以直接执行的低风险修改。
- `preview`：需要用户确认的批量或破坏性修改。
- `answer`：只回答问题，不改图。
- `clarify`：信息不足，先追问。

### 7.3 面向用户的变化协议

不要继续让模型直接操作 `Partial<KnowledgeNode>`。使用语义化变化：

- `rename_graph`
- `rename_node`
- `rewrite_node_description`
- `emphasize_node`
- `move_node`
- `remove_nodes`
- `merge_nodes`
- `rewrite_consensus`
- `set_presentation`
- `relayout`

模型只输出节点和分组的真实 ID，服务端负责把语义变化转换成内部 graph patch。

### 7.4 风险分级

低风险，直接执行：

- 改标题
- 改颜色和线条
- 强调一个节点
- 精简一条描述

中风险，展示摘要后执行：

- 批量改写多个节点
- 移动节点分组
- 局部重新布局

高风险，必须确认：

- 删除节点
- 合并节点
- 删除一组共识
- 大范围重写路线

删除类操作必须展示节点名称和理由，例如“引用重复／内容无独立信息／与另一节点语义重复”。

### 7.5 原子提交与版本控制

- 低风险单操作可以直接应用。
- 结构性多操作先完整预检，任一步失败则整组不提交。
- 每次请求携带 `graphVersion` 或 `baseGraphHash`。
- 服务端发现当前图已变化时拒绝覆盖，要求基于最新图重试。
- 前端保存 graph history，撤销由 UI 控制，不交给模型自由调用 `reset`。

### 7.6 局部重渲染

- 改文字：保留节点位置，只更新对应文本。
- 改强调：保留位置，只更新样式。
- 改分组：只重排受影响分组。
- 新增、删除、合并：局部重排。
- 用户明确要求重新布局：才全图布局。

同时记录用户手动编辑的坐标，避免普通 Agent 修改覆盖用户排版。

### 7.7 模型上下文瘦身

不要每次传完整原文和完整 graph。默认传：

- 图标题和摘要
- 节点目录：ID、标签、分组、一句话描述
- 引用标题和 URL 标识
- 最近一次变化记录
- 当前用户请求

只有需要重写具体节点时，才追加相关节点的引用文本。

## 8. 黑客松 MVP 优先级

资源冲突时按以下顺序取舍：先保住双模式生成和基础助手编辑，再完成收藏夹学习路线这一差异化闭环，最后增加复杂结构编辑和真正流式输出。收藏接口尚未真实联调，若受授权或数据可用性阻塞，使用用户自选知乎回答作为明确标注的降级入口，不伪造收藏数据。

### P0：必须完成

1. 去掉智能编排用户入口，固定为观点对照和学习路线。
2. 两条模式使用专用 Prompt 和专用质量校验。
3. 看山助手支持改标题、精简共识、突出节点、调整风格。
4. 增加 `answer` 和 `clarify`，避免所有请求都强行改图。
5. 结构修改使用预览确认。
6. 普通内容修改不触发全图重排。
7. 真实来源、引用和个人数据隔离。

### P1：有时间再做

1. 收藏夹到学习路线。
2. “删掉最弱观点”的候选预览。
3. 关注答主过滤和对照视图。
4. 局部重排和 graph version 冲突处理。
5. 真流式完整卡片提交。

### 暂不做

- 自动人格画像
- 多 Agent 辩论
- 任意图类型
- 自动判断用户掌握程度
- 复杂多人协作

## 9. 演示路径

推荐演示顺序：

1. 用户使用知乎登录。
2. 选择一个收藏夹或输入“我想做出一个 Agent”。
3. 系统展示资料如何被整理成学习路线。
4. 点开一个阶段，回到知乎原文。
5. 切换到观点对照，展示关注答主与其他观点的差异。
6. 对看山助手说“删掉最弱的观点”。
7. 助手列出候选和理由，用户确认后再修改画布。
8. 对助手追问“这个分歧的关键前提是什么”，助手只回答，不乱改图。

这条路径同时展示：知乎生态、AI 场景价值、可解释性、完成度和安全的编辑体验。

## 10. 验收标准

### 生成

- 两种模式各有清晰目标，不出现无意义凑数节点。
- 每个关键节点都有真实引用。
- 观点结构不强制正反二分。
- 路线节点包含可执行任务和验证方式。
- 失败时展示来源和可理解的错误。

### 助手

- 低风险修改成功率优先于操作种类数量。
- 解释类问题不会改变 graph。
- 删除和合并类操作不会未经确认提交。
- 单点文字修改不改变无关节点位置。
- 非法 ID、未知引用和版本冲突不会破坏当前图。
- 每次响应能明确显示已执行、未执行和需要确认的变化。

### 产品

- 未登录用户仍可体验基础观点对照。
- 登录后至少有一个明显改变结果的个性化能力。
- 个人收藏和学习标记默认私密。
- 分享内容不泄露 OAuth token、个人私密数据或内部 ID。

## 11. 实施顺序

1. 先固定产品入口和两条模式的验收标准。
2. 把看山助手协议统一为语义化变化，并保留旧协议兼容转换。
3. 增加 `answer`、`clarify`、preview/confirm 和原子提交。
4. 加入局部重渲染和 graph version 防覆盖。
5. 用 10 个真实问题建立观点对照和学习路线评测集。
6. 对比 DeepSeek V4 Flash、知乎直答快速模型和可用强模型的延迟与质量。
7. 最后实现收藏夹学习路线和关注答主增强。

此文档是产品和技术方案，不等同于已经实施。实施前应单独拆分计划并逐项验证，避免在黑客松临近时同时重构生成链、OAuth 数据层和画布渲染层。
